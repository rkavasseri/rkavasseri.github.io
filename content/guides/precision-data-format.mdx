## 1. Why Precision Matters

Every tensor in your model — weights, activations, gradients, optimizer states — is stored as an array of numbers. The **format** you choose for those numbers creates a three-way tradeoff that affects everything:

```
                    ┌─────────────┐
                    │  PRECISION  │
                    │  (accuracy) │
                    └──────┬──────┘
                           │
              choose any two
                           │
              ┌────────────┼────────────┐
              │                         │
       ┌──────┴──────┐          ┌───────┴─────┐
       │    SPEED    │          │   MEMORY    │
       │ (throughput)│          │  (capacity) │
       └─────────────┘          └─────────────┘
```

Concretely, moving eligible operations from FP32 to BF16 for training commonly gives you:

- **Higher Tensor Core throughput** — BF16 Tensor Core peaks are roughly 2× the TF32 figure on A100 and H100, though realized speedup depends on the workload.
- **Lower memory traffic** — each value occupies 2 bytes instead of 4, which reduces activation memory and bandwidth pressure.
- **Small accuracy impact for many workloads** — with sound mixed-precision technique, final model quality is often close to an FP32 baseline, but this should be measured rather than assumed.

That's not a free lunch — it's an engineering lunch. Understanding *why* it works (and when it doesn't) is what this guide is about.

<Callout type="info">
  Throughout this guide it helps to separate five different kinds of claim:
  a **format property** is fixed by the representation; a **hardware
  capability** depends on the GPU architecture; a **framework policy** depends
  on the PyTorch/CUDA version; a **training recipe** depends on the
  implementation; and **observed model quality** must be measured
  experimentally. Most precision confusion comes from treating one of these as
  though it were another.
</Callout>

## 2. How Floating Point Works

### 2.1 The Anatomy of a Floating Point Number

Every floating point number has three fields packed into a fixed number of bits:

```
┌──────┬──────────────┬──────────────────────────┐
│ Sign │   Exponent   │        Mantissa          │
│ (1b) │   (E bits)   │        (M bits)          │
└──────┴──────────────┴──────────────────────────┘
```

The value is calculated as:

```
value = (-1)^sign × 2^(exponent - bias) × (1 + mantissa)
```

Each field controls something different:

| Field | Bits | Controls | More bits means |
|---|---|---|---|
| **Sign** | Always 1 | Positive or negative | — |
| **Exponent** | E | Dynamic range — how large/small numbers can be | Wider range of magnitudes |
| **Mantissa** | M | Precision — how many significant digits | Finer distinctions between close values |

### 2.2 Why This Matters for ML

Different parts of an ML pipeline have different needs:

- **Weights** are typically small values clustered near zero. They need reasonable *precision* (mantissa) to capture fine updates during training, but don't need extreme *range* (exponent).
- **Activations** can span a wide dynamic range (especially before normalization layers). They benefit from a wide *exponent*.
- **Gradients** during backpropagation can be very small (vanishing) or very large (exploding). They need both *range* and *precision*.
- **Optimizer states** (like Adam's running mean/variance) accumulate statistics over time and are sensitive to rounding — they need high *precision*.
- **Loss values** are scalar numbers that can vary widely — moderate requirements.

This is exactly why *mixed* precision works: use high precision where it matters, low precision where speed matters, and you get the best of both.

## 3. The Formats — From FP64 to FP4

### 3.1 Format Overview

```
FP64  ┌─┬───────────────┬────────────────────────────────────────────────────────┐
      │S│  Exponent(11) │                   Mantissa (52)                        │  64 bits
      └─┴───────────────┴────────────────────────────────────────────────────────┘

FP32  ┌─┬──────────┬───────────────────────────┐
      │S│  Exp (8) │      Mantissa (23)        │  32 bits
      └─┴──────────┴───────────────────────────┘

TF32  ┌─┬──────────┬────────────┐
      │S│  Exp (8) │  Mant (10) │  FP32 storage; reduced-precision Tensor Core input
      └─┴──────────┴────────────┘

FP16  ┌─┬───────┬────────────┐
      │S│Exp(5) │  Mant (10) │  16 bits
      └─┴───────┴────────────┘

BF16  ┌─┬──────────┬────────┐
      │S│  Exp (8) │Mant(7) │  16 bits
      └─┴──────────┴────────┘

FP8   ┌─┬──────┬─────┐
(E4M3)│S│Exp(4)│Mt(3)│  8 bits — for forward pass (weights, activations)
      └─┴──────┴─────┘

FP8   ┌─┬───────┬────┐
(E5M2)│S│Exp(5) │M(2)│  8 bits — for backward pass (gradients)
      └─┴───────┴────┘
```

> **TF32 is not a 19-bit storage datatype.** Tensors remain FP32 in memory. For
> eligible Tensor Core operations, FP32 inputs are rounded to TF32 precision —
> an 8-bit exponent and 10 explicit fraction bits — while accumulation is
> typically performed in FP32.

### 3.2 Detailed Comparison

| Format | Bits | Exponent | Fraction | Dynamic Range | Approx. Decimal Precision | GPU Support |
|---|---|---|---|---|---|---|
| **FP64** | 64 | 11 | 52 | ±1.8×10^308 | ~15–16 digits | Broad GPU support; throughput varies greatly |
| **FP32** | 32 | 8 | 23 | ±3.4×10^38 | ~7 digits | Broad |
| **TF32** | FP32 storage* | 8 | 10 used for Tensor Core input | FP32 range | ~3 digits input precision | NVIDIA Ampere and later |
| **FP16** | 16 | 5 | 10 | ±65,504 | ~3 digits | Modern GPUs |
| **BF16** | 16 | 8 | 7 | ~FP32 range | ~2–3 digits | NVIDIA Ampere and later; other modern accelerators |
| **FP8 E4M3** | 8 | 4 | 3 | ±448 | ~1–2 digits | Supported FP8 hardware, including NVIDIA Ada/Hopper/Blackwell |
| **FP8 E5M2** | 8 | 5 | 2 | ±57,344 | ~1 digit | Supported FP8 hardware, including NVIDIA Ada/Hopper/Blackwell |
| **INT8** | 8 | — | — | -128 to 127 signed | — | Broad |
| **INT4** | 4 | — | — | -8 to 7 signed | — | Hardware/framework dependent |

*TF32 uses FP32 tensors as inputs and storage. Eligible Tensor Core operations
reduce the input significand precision while retaining FP32-like exponent range
and typically accumulating into FP32.

### 3.3 Deep Dive: Each Format

#### FP64 (Double Precision)

```python
x = torch.tensor(1.0, dtype=torch.float64)

# 52-bit fraction → ~15–16 decimal digits of precision
# Common in: scientific computing, numerical solvers,
#            numerical validation and precision-sensitive algorithms
# Uncommon in: conventional deep neural-network training
```

FP64 is uncommon in conventional deep-learning training because it doubles memory relative to FP32 and usually provides little model-quality benefit while substantially reducing throughput on many GPUs. It remains important in scientific ML, numerical solvers, ill-conditioned computations, validation, and applications where numerical precision is itself part of the problem. In a conventional neural-network pipeline, an unexpected `float64` tensor is often worth checking for accidental dtype promotion.

#### FP32 (Single Precision)

```python
x = torch.tensor(1.0, dtype=torch.float32)  # this is the default
# 23-bit mantissa → ~7 decimal digits
# Range: ±3.4 × 10^38
```

The historical default for neural network training. Perfectly adequate for all ML tasks, but you're leaving performance on the table if you use it for everything on A100/H100.

#### TF32 (TensorFloat-32)

```
TF32 = FP32 range + FP16 precision
```

TF32 is not a storage format — it is a hardware compute mode for selected FP32 operations on NVIDIA Ampere and later GPUs. Tensors remain FP32 in memory. For eligible matrix multiplications and convolutions, Tensor Cores can use TF32-like input precision while retaining FP32 dynamic range and FP32 accumulation.

<Callout type="warning">
  **Do not assume TF32 has one global PyTorch default.** Matrix multiplication
  and cuDNN operations have historically had different defaults, and PyTorch's
  control API has evolved. In PyTorch 1.12 and later, the legacy
  `torch.backends.cuda.matmul.allow_tf32` setting defaults to `False`, while
  cuDNN TF32 has historically defaulted to `True`.
</Callout>

```python
# Current PyTorch exposes more explicit FP32 precision controls.
# Exact availability depends on PyTorch version.

torch.backends.cuda.matmul.fp32_precision = "tf32"
torch.backends.cudnn.conv.fp32_precision = "tf32"

# If strict IEEE FP32 behavior is required:
torch.backends.cuda.matmul.fp32_precision = "ieee"
torch.backends.cudnn.conv.fp32_precision = "ieee"
```

Key points:
- No parameter-storage savings: tensors remain FP32.
- Can accelerate eligible FP32 matrix multiplication and convolution workloads on Ampere and later NVIDIA GPUs.
- Uses FP32-like exponent range with reduced input significand precision.
- Accumulation is performed with FP32 precision.
- Whether TF32 is enabled should be treated as an explicit runtime/framework setting rather than assumed.

Think of TF32 as a hardware-accelerated execution path for eligible FP32 workloads when its reduced input precision is acceptable.

#### FP16 (Half Precision)

```python
x = torch.tensor(1.0, dtype=torch.float16)
# 10-bit mantissa → ~3 decimal digits
# Range: ±65,504  ← THIS IS THE PROBLEM
```

FP16 is fast and memory-efficient, but the 5-bit exponent limits the dynamic range to ±65,504. In practice, this means:

- **Overflow**: Loss values, logits, or activations exceeding 65,504 become `inf`.
- **Underflow**: FP16's minimum positive **normal** value is approximately `6.10×10^-5`; subnormal values extend down to approximately `5.96×10^-8`. Very small gradients can therefore lose precision or eventually underflow to zero.
- **Loss scaling is commonly used for FP16 training** and is often essential for numerical robustness. `GradScaler` scales the loss before backpropagation so small gradient values are less likely to underflow, then unscales them before the optimizer update.

FP16 remains useful and well supported, particularly on hardware without BF16 acceleration. On hardware with strong BF16 support, BF16 is often the easier training default because its wider exponent range substantially reduces overflow and underflow problems.

#### BF16 (Brain Floating Point)

```python
x = torch.tensor(1.0, dtype=torch.bfloat16)
# 7-bit mantissa → ~2 decimal digits
# Range: ±3.4 × 10^38  ← SAME AS FP32
```

BF16 was designed by Google Brain specifically for deep learning. The key insight: **dynamic range matters more than precision for training neural networks.**

```
BF16 vs FP16:
  BF16:  fewer precise digits (7-bit mantissa)
  BF16:  same range as FP32 (8-bit exponent)  ← this wins
  FP16:  more precise digits (10-bit mantissa)
  FP16:  narrow range (5-bit exponent)         ← this causes problems
```

Because BF16 uses the same 8-bit exponent width as FP32, it has approximately the same dynamic range. It therefore avoids FP16's 65,504 overflow limit and makes gradient underflow far less problematic than in FP16. BF16 still has finite range and limited precision, so overflow, underflow, and rounding remain possible.

Loss scaling is generally unnecessary for BF16 training. On GPUs with efficient BF16 Tensor Core support — including NVIDIA A100 and H100 — BF16 mixed precision is an excellent default for many deep-learning workloads.

```python
# BF16 generally does not require gradient scaling
with torch.amp.autocast(device_type="cuda", dtype=torch.bfloat16):
    output = model(input)
    loss = criterion(output, target)

loss.backward()      # just works — no scaling needed
optimizer.step()
```

#### FP8 (E4M3 and E5M2)

FP8 provides only eight bits per value and therefore requires scaling to keep tensors within a useful representable range. Two common formats are E4M3 and E5M2.

NVIDIA Transformer Engine's traditional **HYBRID** FP8 recipe uses:

- **E4M3** for the forward pass, where additional precision is useful.
- **E5M2** for the backward pass, where additional dynamic range can be useful.

This mapping is a training recipe rather than an intrinsic rule of the FP8 formats. Modern scaling strategies can also use E4M3 in both directions.

```
E4M3:  4-bit exponent, 3-bit mantissa → range ±448
       Used for: forward pass (weights and activations)
       More precision, less range

E5M2:  5-bit exponent, 2-bit mantissa → range ±57,344
       Used for: backward pass (gradients)
       Less precision, more range (gradients vary more widely)
```

NVIDIA Transformer Engine supports FP8 on **Ada, Hopper, and Blackwell** GPUs. FP8 execution is architecture- and software-dependent; NVIDIA's Transformer Engine provides scaling recipes and optimized layers that make FP8 training practical.

FP8 can substantially increase Tensor Core throughput relative to BF16 on supported hardware, although application-level speedup depends on model shape, scaling overhead, memory traffic, kernel coverage, and how much of the workload actually executes in FP8.

```python
# FP8 via NVIDIA Transformer Engine on supported Ada/Hopper/Blackwell GPUs
import transformer_engine.pytorch as te

# Replace standard PyTorch layers
linear = te.Linear(1024, 4096)

with te.fp8_autocast(enabled=True):
    output = linear(input)
    # TE handles per-tensor scaling internally
```

On Blackwell, newer block-scaled formats such as MXFP8 further change the precision/scaling tradeoff. FP8 should therefore be understood as a family of low-precision execution strategies, not simply as "E4M3 forward / E5M2 backward."

FP8 is not a "set and forget" format. It works best for:
- Transformer architectures (attention + feedforward layers).
- Large models where throughput is critical.
- When you've already optimized everything else.

#### INT8 and INT4 (Integer Quantization)

Integer formats have no exponent — they represent a fixed, evenly-spaced set of values. A separate *scale factor* maps them back to the real number line:

```
quantized_value = round(real_value / scale) + zero_point

real_value ≈ (quantized_value - zero_point) × scale
```

The zero point is expressed in the **quantized integer domain**: it identifies the integer code corresponding to real-valued zero.

```python
# INT8: 256 distinct values (-128 to 127)
# INT4: 16 distinct values (-8 to 7)

# These are primarily used for INFERENCE, not training
# See Section 10: Quantization
```

## 4. Memory & Storage Impact

### 4.1 Bytes Per Element

| Format | Bytes | Relative to FP32 |
|---|---|---|
| FP64 | 8 | 2× |
| FP32 | 4 | 1× (baseline) |
| FP16 / BF16 | 2 | 0.5× |
| FP8 | 1 | 0.25× |
| INT8 | 1 | 0.25× |
| INT4 | 0.5 | 0.125× |

### 4.2 Model Memory Calculator

A training workload usually consumes GPU memory in several major categories:

```
Total Memory ≈ Parameters
             + Gradients
             + Optimizer State
             + Saved Activations
             + Temporary Buffers / Workspace
```

The exact dtype of each component depends on the training strategy.

#### Standard PyTorch AMP / autocast

A common pattern is:

```python
model = model.cuda()  # parameters remain FP32

with torch.autocast("cuda", dtype=torch.bfloat16):
    output = model(input)
    loss = criterion(output, target)

loss.backward()
optimizer.step()
```

Here, the model parameters remain FP32. `autocast` selects lower-precision execution for eligible operations; it does **not** normally maintain one persistent BF16 parameter tensor plus a second FP32 "master weight" tensor.

For a 1-billion-parameter model using conventional FP32 parameters and Adam:

| Component | Approximate fixed memory | Notes |
|---|---|---|
| Parameters | 4 GB | FP32 parameters |
| Gradients | ~4 GB | Often match parameter storage in conventional AMP |
| Adam first moment | 4 GB | Typically FP32 |
| Adam second moment | 4 GB | Typically FP32 |
| Activations | Varies | Autocast can significantly reduce this component |
| Temporary buffers | Varies | Kernel/framework dependent |

This gives roughly **16 GB plus activations and temporary memory** before considering distributed-training sharding or other optimizations.

The major memory benefit of ordinary AMP often comes from reduced-precision intermediate activations and temporary tensors rather than automatically halving every persistent training tensor.

#### Alternative low-precision parameter strategies

Some frameworks and large-model training systems deliberately store parameters or optimizer state in reduced precision, maintain explicit FP32 master weights, shard state across GPUs, or quantize optimizer states. Those are separate implementation choices and can produce very different memory accounting.

### 4.3 Quick Estimation Script

```python
def estimate_memory(
    num_params_billions,
    param_bytes=4,
    grad_bytes=4,
    optimizer_state_bytes_per_param=8,
):
    """
    Approximate persistent training-state memory.
    Excludes activations, temporary buffers, fragmentation,
    communication buffers, and framework-specific overhead.
    """
    P = num_params_billions * 1e9

    params = P * param_bytes
    grads = P * grad_bytes
    optimizer = P * optimizer_state_bytes_per_param

    total = params + grads + optimizer
    GB = 1e9

    print(f"{num_params_billions}B parameters")
    print(f"  Parameters: {params / GB:.1f} GB")
    print(f"  Gradients:  {grads / GB:.1f} GB")
    print(f"  Optimizer:  {optimizer / GB:.1f} GB")
    print(f"  Fixed total:{total / GB:.1f} GB")
    print("  + activations, temporary buffers, and runtime overhead")


# Conventional FP32-parameter Adam / standard AMP-style accounting
estimate_memory(
    1.0,
    param_bytes=4,
    grad_bytes=4,
    optimizer_state_bytes_per_param=8,
)
```

<Callout type="warning">
  Do not infer total training memory solely from the compute dtype.
  `autocast(dtype=torch.bfloat16)` describes how eligible operations execute; it
  does not by itself specify how parameters, gradients, optimizer states,
  checkpoints, or distributed shards are stored.
</Callout>

### 4.4 Checkpoint & Storage Sizes

Saving a model checkpoint means writing all parameters (and optionally optimizer state) to disk:

| Model Size | FP32 Checkpoint | BF16 Checkpoint | INT4 (inference) |
|---|---|---|---|
| 125M params | 500 MB | 250 MB | 62 MB |
| 1B params | 4 GB | 2 GB | 500 MB |
| 7B params | 28 GB | 14 GB | 3.5 GB |
| 70B params | 280 GB | 140 GB | 35 GB |

```python
# Save in BF16 to cut checkpoint size in half
model_bf16 = model.to(torch.bfloat16)
torch.save(model_bf16.state_dict(), "model_bf16.pt")

# Save in FP32 (default)
torch.save(model.state_dict(), "model_fp32.pt")
```

## 5. Speed & Throughput Impact

### 5.1 Tensor Core Throughput — Representative Dense Peak

The GPU's tensor cores are specialized hardware for matrix multiply-accumulate. Different precisions run at different speeds.

Peak specifications depend on GPU SKU, clock/power configuration, datatype, accumulation mode, and whether NVIDIA's 2:4 structured sparsity is enabled. The table below uses representative **dense** peak values and should be treated as hardware capability, not expected application throughput.

| Precision | A100 | H100 SXM | Notes |
|---|---|---|---|
| FP64 CUDA cores | 9.7 TFLOPS | 34 TFLOPS | Dense |
| FP32 CUDA cores | 19.5 TFLOPS | 67 TFLOPS | Dense |
| TF32 Tensor Core | 156 TFLOPS | ~495 TFLOPS | Dense |
| BF16 Tensor Core | 312 TFLOPS | ~989 TFLOPS | Dense |
| FP16 Tensor Core | 312 TFLOPS | ~989 TFLOPS | Dense |
| FP8 Tensor Core | — | ~1,979 TFLOPS | Dense |
| INT8 Tensor Core | 624 TOPS | ~1,979 TOPS | Dense |

NVIDIA also publishes approximately 2× higher **effective** Tensor Core figures when supported 2:4 structured sparsity is used. Dense and sparsity-assisted numbers should not be mixed in the same comparison.

### 5.2 Real-World Speedups

Theoretical TFLOPS rarely translate directly. Here are realistic multipliers for typical training workloads:

| Switching from → to | Typical Speedup | Why not higher? |
|---|---|---|
| FP32 → TF32 | 1.5–3× | Only matmuls benefit; rest is FP32 |
| FP32 → BF16 mixed | 1.5–2.5× | Memory bandwidth + non-matmul ops limit |
| BF16 → FP8 (H100) | 1.3–1.8× | Scaling overhead; not all layers use FP8 |
| FP32 → INT8 (inference) | 2–4× | Entire model runs in INT8; memory-bound speedup |

### 5.3 Measuring Throughput

```python
import torch
import time

def benchmark_matmul(M, N, K, dtype, warmup=50, iters=200):
    """Benchmark matrix multiplication at a given precision."""
    A = torch.randn(M, K, device="cuda", dtype=dtype)
    B = torch.randn(K, N, device="cuda", dtype=dtype)

    # Warmup
    for _ in range(warmup):
        torch.mm(A, B)
    torch.cuda.synchronize()

    # Time it
    start = time.perf_counter()
    for _ in range(iters):
        torch.mm(A, B)
    torch.cuda.synchronize()
    elapsed = time.perf_counter() - start

    flops = 2 * M * N * K * iters
    tflops = flops / elapsed / 1e12
    print(f"  {str(dtype):20s} → {tflops:.1f} TFLOPS  ({elapsed/iters*1000:.2f} ms/iter)")
    return tflops

print("Matrix multiplication benchmark (4096 × 4096 × 4096):")
for dtype in [torch.float32, torch.float16, torch.bfloat16]:
    benchmark_matmul(4096, 4096, 4096, dtype)
```

### 5.4 Why Memory Bandwidth Often Matters More Than Compute

Modern GPUs are **compute-bound** for large matmuls but **memory-bound** for everything else (element-wise ops, normalization, attention scores, small layers). When you're memory-bound, using a smaller data type helps because you're moving fewer bytes:

```
FP32: 4 bytes per element → X GB/s ÷ 4 = Y elements/s
BF16: 2 bytes per element → X GB/s ÷ 2 = 2Y elements/s  (2× throughput)
```

This is why mixed precision helps even for operations that don't use tensor cores.

## 6. Accuracy & Numerical Stability

### 6.1 Precision vs Accuracy — What You Actually Lose

When you drop from FP32 to BF16, you lose **mantissa bits** (23 → 7). This means:

```python
import torch

# FP32 can distinguish these two values:
a_fp32 = torch.tensor(1.0000001, dtype=torch.float32)
b_fp32 = torch.tensor(1.0000002, dtype=torch.float32)
print(f"FP32: {a_fp32.item()} ≠ {b_fp32.item()}")  # different

# BF16 cannot:
a_bf16 = torch.tensor(1.0000001, dtype=torch.bfloat16)
b_bf16 = torch.tensor(1.0000002, dtype=torch.bfloat16)
print(f"BF16: {a_bf16.item()} == {b_bf16.item()}")  # same! both round to 1.0
```

In machine learning, this *usually* doesn't matter because:
- Gradient updates are noisy anyway (stochastic gradient descent).
- Neural networks are robust to small perturbations.
- The direction of the gradient matters more than its exact magnitude.

### 6.2 When Reduced Precision DOES Cause Problems

Some operations are sensitive to precision. The mixed-precision strategy keeps these in FP32:

| Operation | Why it needs FP32 | What happens in FP16/BF16 |
|---|---|---|
| **Loss computation** | Small loss differences vanish | Training stalls |
| **Softmax** | Exponentiation of large values | Overflow / NaN |
| **Layer normalization** | Variance computation with subtraction | Catastrophic cancellation |
| **Small learning rate updates** | weight += lr × gradient may underflow | Weights stop updating |
| **Accumulation (sum/mean)** | Rounding errors accumulate | Drift over millions of steps |

### 6.3 Catastrophic Cancellation — The Sneaky Bug

When you subtract two nearly equal numbers, you lose significant digits:

```python
import torch

# FP32: fine
a = torch.tensor(1.000001, dtype=torch.float32)
b = torch.tensor(1.000000, dtype=torch.float32)
print(f"FP32: {(a - b).item():.10f}")  # 0.0000010000 ✓

# BF16: disaster
a = torch.tensor(1.000001, dtype=torch.bfloat16)
b = torch.tensor(1.000000, dtype=torch.bfloat16)
print(f"BF16: {(a - b).item():.10f}")  # 0.0000000000 ✗ (both rounded to 1.0)
```

This is why normalization layers (which compute `x - mean(x)`) are kept in FP32 during mixed precision training.

### 6.4 Swamping — Death by Accumulation

When you add a very small number to a very large one, the small number gets lost:

```python
# Simulating gradient accumulation in BF16 vs FP32
big = torch.tensor(1000.0, dtype=torch.bfloat16)
small = torch.tensor(0.01, dtype=torch.bfloat16)

result = big + small
print(f"BF16: 1000.0 + 0.01 = {result.item()}")  # still 1000.0 — the 0.01 vanished

# This is one reason conventional training commonly keeps
# accumulation-sensitive optimizer state in FP32.
```

FP32 optimizer state is common, particularly for Adam/AdamW, but it is not a universal requirement. Reduced-precision and quantized optimizer implementations also exist.

## 7. Mixed Precision Training — How It Actually Works

### 7.1 The Architecture

Mixed precision is primarily about choosing an appropriate execution precision for each operation while retaining higher precision where numerical stability requires it.

A conventional PyTorch BF16 autocast workflow looks conceptually like this:

```
                     ┌──────────────────────────┐
                     │     MODEL PARAMETERS     │
                     │        typically FP32    │
                     └────────────┬─────────────┘
                                  │
                                  ▼
                     ┌──────────────────────────┐
Input ──────────────▶│   AUTOCAST REGION        │──────────────▶ Output
                     │                          │
                     │ Eligible GEMMs / convs   │
                     │      → BF16              │
                     │                          │
                     │ Sensitive operations     │
                     │      → FP32 as needed    │
                     └────────────┬─────────────┘
                                  │
                                  ▼
                           BACKPROPAGATION
                                  │
                                  ▼
                     ┌──────────────────────────┐
                     │     OPTIMIZER STEP       │
                     │ conventional optimizer   │
                     │ state often FP32         │
                     └──────────────────────────┘
```

<Callout type="info">
  `autocast` is an operation-dispatch mechanism. It does not simply convert the
  entire model to BF16, nor does it imply that a second FP32 master copy of
  every parameter exists.

  Explicit low-precision parameter storage plus FP32 master weights is another
  valid mixed-precision architecture, but it should be distinguished from
  standard PyTorch autocast.
</Callout>

### 7.2 What autocast Does and Doesn't Do

`torch.amp.autocast` selectively casts operations to lower precision. Not all operations are cast — PyTorch maintains an internal list:

```python
# Examples of CUDA operations eligible for lower-precision autocast:
#   matmul, mm, bmm
#   linear
#   conv1d / conv2d / conv3d
#
# Examples that PyTorch's CUDA autocast policy can execute in FP32
# for numerical stability:
#   softmax / log_softmax
#   cross_entropy
#   layer_norm / group_norm
#   normalize
#   sum
#   binary_cross_entropy_with_logits
#
# Unlisted operations generally run according to their input dtype.
# Exact autocast policy is framework/version dependent.
```

PyTorch specifically recommends `binary_cross_entropy_with_logits` rather than `binary_cross_entropy` inside autocast-sensitive training code.

```python
with torch.amp.autocast(device_type="cuda", dtype=torch.bfloat16):
    hidden = model.linear(x)
    hidden = model.layernorm(hidden)
    attn = torch.softmax(scores, dim=-1)
    loss = criterion(logits, targets)

# Do not assume every intermediate tensor's visible dtype tells you
# the internal arithmetic precision of every kernel.
```

### 7.3 GradScaler — When and Why

`GradScaler` is primarily associated with FP16 mixed-precision training. FP16's narrow exponent range makes small gradients particularly vulnerable to underflow. Loss scaling shifts gradient magnitudes into a more useful representable range during backpropagation.

BF16 has a much wider exponent range, so gradient scaling is generally unnecessary for BF16 training.

GradScaler is commonly used — and often practically necessary — for robust FP16 training. It is generally unnecessary for BF16:

```python
scaler = torch.amp.GradScaler()

# 1. Scale the loss UP before backward (keeps gradients representable)
scaler.scale(loss).backward()

# 2. Unscale gradients back DOWN before clipping
scaler.unscale_(optimizer)
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)

# 3. Step — skips if any gradients are inf/nan (from overflow)
scaler.step(optimizer)

# 4. Update the scale factor for next iteration
scaler.update()
```

With BF16, gradient underflow is far less problematic because BF16 shares FP32's exponent width, so gradient scaling is generally unnecessary.

### 7.4 FP32 Master Weights — An Alternative Pattern

Some mixed-precision implementations store working parameters in a low-precision format while maintaining a separate FP32 master copy for optimizer updates. The motivation is straightforward: an update may be too small to change a BF16 or FP16 parameter directly.

```python
# Suppose:
weight = 10.0  (BF16)
lr = 1e-4
gradient = 0.5
update = lr * gradient = 0.00005

# In BF16:
# 10.0 + 0.00005 = 10.0  ← the update vanished (swamped)

# In FP32:
# 10.0 + 0.00005 = 10.00005  ← update preserved

# After many steps, FP32 master weights have accumulated many small updates.
# Cast to BF16 for the next forward pass.
```

In an explicit master-weight implementation, the optimizer updates FP32 master parameters and new low-precision working weights are produced from them. **Standard PyTorch autocast does not require this architecture:** parameters can remain FP32 while eligible operations execute internally at BF16 or FP16 precision.

## 8. Format Selection Guide

### 8.1 Decision Tree

```
Are you TRAINING or running INFERENCE?
│
├─ TRAINING
│   │
│   ├─ Does your accelerator provide efficient BF16 support?
│   │   │
│   │   ├─ Yes → BF16 autocast is a strong default for training.
│   │   │         Configure TF32 explicitly if using FP32 matmuls/convs
│   │   │         and its precision is acceptable.
│   │   │         Consider FP8 on supported hardware when additional
│   │   │         throughput justifies the scaling/validation complexity.
│   │   │
│   │   └─ No → FP16 mixed precision with GradScaler is often the
│   │            appropriate Tensor Core training path.
│   │
│   └─ Special cases:
│       ├─ Numerical debugging → Pure FP32 (disable TF32 too)
│       ├─ Scientific computing → FP64
│       └─ Training is unstable → Try FP32 first to isolate the issue
│
└─ INFERENCE
    │
    ├─ Latency-sensitive (real-time)?
    │   ├─ Yes → INT8 or INT4 quantization
    │   └─ No  → BF16 (simple, accurate)
    │
    └─ Memory-constrained (large model, small GPU)?
        ├─ Moderate → INT8: approximately 2× raw weight-storage
        │              reduction vs FP16/BF16
        └─ Severe   → INT4 / GPTQ / AWQ: approximately 4× raw
                       weight-storage reduction

    Always measure model/task quality after quantization.
```

### 8.2 Summary Table

| Use Case | Typical Format | Notes |
|---|---|---|
| Default training on strong BF16 hardware | BF16 autocast | Excellent range/performance tradeoff |
| Training on FP16-oriented hardware | FP16 autocast | Usually pair with GradScaler |
| Conventional Adam/AdamW state | FP32 commonly used | Not a universal requirement |
| Standard PyTorch AMP parameters | Often FP32 | Autocast changes execution precision, not necessarily parameter storage |
| Numerical debugging | FP32 / FP64 as appropriate | Disable reduced-precision execution when isolating numerical issues |
| Maximum-throughput Transformer training | FP8 on supported hardware | Requires appropriate scaling and validation |
| Quality-first inference | BF16 / FP16 / FP32 | Hardware and model dependent |
| Quantized inference | INT8 / INT4 / FP8 | Validate latency, memory, and task quality |
| Compact checkpoint storage | BF16/FP16 or quantized | Depends on intended reuse |

### 9.2 Autocast Patterns

```python
from torch.amp import autocast, GradScaler

# BF16
with autocast(device_type="cuda", dtype=torch.bfloat16):
    output = model(input)
    loss = criterion(output, target)

loss.backward()
optimizer.step()


# FP16
scaler = GradScaler("cuda")

with autocast(device_type="cuda", dtype=torch.float16):
    output = model(input)
    loss = criterion(output, target)

scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()


# Selective autocast — force FP32 for a numerically sensitive layer
with autocast(device_type="cuda", dtype=torch.bfloat16):
    features = model.backbone(images)
    with autocast(device_type="cuda", enabled=False):
        features_fp32 = features.float()

    loss = criterion(output, target)
```

BF16 autocast does not create BF16 model parameters; it selects execution precision for eligible operations.

## 10. Quantization for Inference

### 10.1 Why Quantize?

Training is done. Your model works. Now you want to deploy it as fast and cheaply as possible. Quantization compresses the model by representing weights (and optionally activations) in lower-bit integers.

```
Higher precision → simpler numerical behavior, larger raw representation
Lower precision  → lower storage/bandwidth cost, potentially higher throughput

Actual accuracy and speed depend on the model, quantization scheme,
kernel implementation, hardware, calibration, and workload.
```

### 10.2 Post-Training Quantization (PTQ) with PyTorch

```python
import torch

# Static quantization: calibrate with representative data
model.eval()
model_bf16 = model.to(torch.bfloat16)

# Dynamic quantization (simplest — quantizes weights, activations stay FP32)
from torch.ao.quantization import quantize_dynamic

model_int8 = quantize_dynamic(
    model,
    {torch.nn.Linear},     # which layers to quantize
    dtype=torch.qint8,
)
```

### 10.3 GPTQ, AWQ, and Friends (for Large Language Models)

For LLMs, specialized quantization methods preserve quality better than naive approaches:

| Method | Bits | Quality | Speed | How it works |
|---|---|---|---|---|
| **GPTQ** | 4 | Good | Fast | Layer-wise weight quantization with error compensation |
| **AWQ** | 4 | Good | Fast | Protects salient weights from aggressive quantization |
| **GGUF** | 2–8 | Varies | CPU-friendly | Used by llama.cpp; multiple quantization levels |
| **SmoothQuant** | 8 | Excellent | Fast | Migrates difficulty from activations to weights |
| **bitsandbytes** | 4/8 | Good | Moderate | NF4 format; popular with QLoRA |

```python
# Example: Loading a 4-bit quantized model with bitsandbytes
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",           # NormalFloat4
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,       # quantize the quantization constants
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-7b-hf",
    quantization_config=bnb_config,
    device_map="auto",
)
# 7B model: ~28 GB in FP32 → ~3.5 GB in 4-bit. Fits on a single GPU.
```

### 10.4 Quantization Quality Checklist

After quantizing, always validate:

```python
# 1. Compare output distributions
with torch.no_grad():
    out_fp32 = model_fp32(sample_input)
    out_int8 = model_int8(sample_input)

    # Max absolute difference
    print(f"Max diff: {(out_fp32 - out_int8).abs().max().item():.6f}")

    # Cosine similarity is a useful diagnostic, but no universal
    # threshold guarantees preserved model quality.
    cos_sim = torch.nn.functional.cosine_similarity(
        out_fp32.flatten().unsqueeze(0),
        out_int8.flatten().unsqueeze(0)
    )
    print(f"Cosine similarity: {cos_sim.item():.6f}")

# 2. Run your evaluation benchmark
#    Compare accuracy/perplexity before and after quantization.
```

Quantization quality must ultimately be assessed on the task metric that matters: accuracy, F1, perplexity, retrieval quality, generation quality, or another application-specific measure.

## 11. Experiments You Can Run

These experiments will build your intuition. Each one is self-contained and runs on a single GPU.

### 11.1 Experiment: Precision Comparison

```python
#!/usr/bin/env python3
"""exp_precision.py — Compare formats on the same training run."""

import torch
import torch.nn as nn
import time
from torchvision import datasets, transforms, models
from torch.utils.data import DataLoader
from torch.amp import autocast, GradScaler


def train_epoch(model, loader, criterion, optimizer, device, precision, scaler=None):
    model.train()
    total_loss = 0
    correct = 0
    total = 0
    t0 = time.perf_counter()

    for images, labels in loader:
        images = images.to(device, non_blocking=True)
        labels = labels.to(device, non_blocking=True)
        optimizer.zero_grad(set_to_none=True)

        if precision == "fp32":
            outputs = model(images)
            loss = criterion(outputs, labels)
            loss.backward()
            optimizer.step()

        elif precision in ("fp16", "bf16"):
            dtype = torch.float16 if precision == "fp16" else torch.bfloat16
            with autocast(device_type="cuda", dtype=dtype):
                outputs = model(images)
                loss = criterion(outputs, labels)
            if scaler:
                scaler.scale(loss).backward()
                scaler.step(optimizer)
                scaler.update()
            else:
                loss.backward()
                optimizer.step()

        total_loss += loss.item() * images.size(0)
        _, pred = outputs.max(1)
        correct += pred.eq(labels).sum().item()
        total += labels.size(0)

    elapsed = time.perf_counter() - t0
    return total_loss / total, correct / total, elapsed


def main():
    device = torch.device("cuda")
    transform = transforms.Compose([
        transforms.Resize(224),
        transforms.ToTensor(),
        transforms.Normalize([0.485, 0.456, 0.406], [0.229, 0.224, 0.225]),
    ])
    dataset = datasets.CIFAR10("./data", train=True, download=True, transform=transform)
    loader = DataLoader(dataset, batch_size=128, num_workers=4, pin_memory=True)

    results = {}
    for precision in ["fp32", "bf16", "fp16"]:
        print(f"\n{'='*50}")
        print(f"Training with {precision.upper()}")
        print(f"{'='*50}")

        model = models.resnet18(num_classes=10).to(device)
        optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)
        criterion = nn.CrossEntropyLoss()
        scaler = GradScaler() if precision == "fp16" else None

        for epoch in range(5):
            loss, acc, elapsed = train_epoch(
                model, loader, criterion, optimizer, device, precision, scaler
            )
            mem = torch.cuda.max_memory_allocated() / 1e9
            print(f"  Epoch {epoch}: loss={loss:.4f} acc={acc:.4f} "
                  f"time={elapsed:.1f}s peak_mem={mem:.2f}GB")

        results[precision] = {"loss": loss, "acc": acc, "time": elapsed, "mem": mem}
        torch.cuda.reset_peak_memory_stats()

    print(f"\n{'='*50}")
    print("Summary:")
    for p, r in results.items():
        print(f"  {p:6s}: acc={r['acc']:.4f}  time={r['time']:.1f}s  mem={r['mem']:.2f}GB")


if __name__ == "__main__":
    main()
```

```python
#!/usr/bin/env python3
"""exp_precision_loss.py — See how formats round differently."""

import torch


def analyze_format(name, dtype, values):
    """Cast values to a format and back, measure the error."""
    original = values.clone()
    converted = values.to(dtype).float()
    error = (original - converted).abs()
    rel_error = error / (original.abs() + 1e-10)
    return {
        "name": name,
        "max_error": error.max().item(),
        "mean_error": error.mean().item(),
        "max_rel_error": rel_error.max().item(),
        "mean_rel_error": rel_error.mean().item(),
    }


# Test with values across different magnitudes
values = torch.cat([
    torch.linspace(1e-8, 1e-4, 1000),    # tiny gradients
    torch.linspace(1e-4, 1.0, 1000),      # typical weights
    torch.linspace(1.0, 1000.0, 1000),    # activations
    torch.linspace(1000.0, 100000.0, 1000), # large values
])

formats = [
    ("FP64", torch.float64),
    ("FP32", torch.float32),
    ("BF16", torch.bfloat16),
    ("FP16", torch.float16),
]

print(f"{'Format':8s} {'Max Abs Error':>15s} {'Mean Abs Error':>15s} "
      f"{'Max Rel Error':>15s} {'Mean Rel Error':>15s}")
print("-" * 72)
for name, dtype in formats:
    try:
        result = analyze_format(name, dtype, values.clone())
        print(f"{result['name']:8s} {result['max_error']:15.8f} "
              f"{result['mean_error']:15.8f} {result['max_rel_error']:15.8f} "
              f"{result['mean_rel_error']:15.8f}")
```

### 11.3 Experiment: Memory Under Different Precisions

```python
#!/usr/bin/env python3
"""exp_memory.py — Measure actual GPU memory for different configurations."""

import torch
import torch.nn as nn
from torchvision import models
from torch.amp import autocast


def measure_memory(model_fn, batch_size, device, precision):
    torch.cuda.reset_peak_memory_stats()
    torch.cuda.empty_cache()

    model = model_fn().to(device)
    optimizer = torch.optim.Adam(model.parameters())
    criterion = nn.CrossEntropyLoss()

    x = torch.randn(batch_size, 3, 224, 224, device=device)
    y = torch.randint(0, 1000, (batch_size,), device=device)

    # Forward + backward
    if precision == "fp32":
        out = model(x)
        loss = criterion(out, y)
        loss.backward()
    else:
        dtype = torch.bfloat16 if precision == "bf16" else torch.float16
        with autocast(device_type="cuda", dtype=dtype):
            out = model(x)
            loss = criterion(out, y)
        loss.backward()

    optimizer.step()
    peak_mem = torch.cuda.max_memory_allocated() / 1e9

    del model, optimizer, x, y, out, loss
    torch.cuda.empty_cache()

    return peak_mem


device = torch.device("cuda")
model_fn = lambda: models.resnet50(num_classes=1000)

print(f"{'Precision':10s} {'Batch 32':>12s} {'Batch 64':>12s} {'Batch 128':>12s}")
print("-" * 48)
for precision in ["fp32", "bf16", "fp16"]:
    mems = []
    for bs in [32, 64, 128]:
        try:
            mem = measure_memory(model_fn, bs, device, precision)
            mems.append(f"{mem:.2f} GB")
        except RuntimeError:
            mems.append("OOM")
    print(f"{precision:10s} {mems[0]:>12s} {mems[1]:>12s} {mems[2]:>12s}")
```

## 12. Troubleshooting Precision Issues

### 12.1 Common Problems and Fixes

| Symptom | Likely Cause | Fix |
|---|---|---|
| `NaN` in loss | FP16 overflow in logits/loss | Switch to BF16 or increase GradScaler `init_scale` |
| Loss stops decreasing | Small gradients underflow in FP16 | Switch to BF16 (wider range) |
| Accuracy is noticeably worse in mixed precision | Sensitive layers cast to low precision | Wrap those layers with `autocast(enabled=False)` |
| `inf` values in activations | Activation/logit overflow or unstable computation | Inspect the producing operation; BF16 may help if FP16 range is the issue. Gradient clipping addresses gradient magnitude and is not a general fix for forward-pass activation overflow |
| Training is slower with AMP than FP32 | Small operations, conversion overhead, poor Tensor Core utilization, CPU/input bottlenecks, unsupported shapes, or a memory-bound workload | Profile the workload and inspect kernel utilization before changing model dimensions |
| GradScaler scale drops to near-zero | Too many inf/nan gradients | Reduce learning rate, check data for corruption |
| `RuntimeError: expected scalar type BFloat16 but found Float` | Dtype mismatch between tensors | Ensure inputs match model dtype; use `autocast` |

### 12.2 Debugging Precision Issues Step by Step

```python
# Step 1: Run in pure FP32 first. Does the problem go away?
# If yes → it's a precision issue. If no → it's a different bug.

# For strict FP32 numerical debugging on current PyTorch:
torch.backends.cuda.matmul.fp32_precision = "ieee"
torch.backends.cudnn.conv.fp32_precision = "ieee"

# Older PyTorch releases use:
# torch.backends.cuda.matmul.allow_tf32 = False
# torch.backends.cudnn.allow_tf32 = False

# Step 2: Check for NaN/Inf
def check_tensors(model, step):
    for name, p in model.named_parameters():
        if p.grad is not None:
            if torch.isnan(p.grad).any():
                print(f"NaN gradient at step {step}: {name}")
            if torch.isinf(p.grad).any():
                print(f"Inf gradient at step {step}: {name}")

# Step 3: Monitor GradScaler (FP16 only)
# If scale keeps dropping, gradients are overflowing
print(f"GradScaler scale: {scaler.get_scale()}")

# Step 4: Identify which layer is producing NaN
# Register hooks to check activations
def nan_hook(module, input, output):
    if isinstance(output, torch.Tensor) and torch.isnan(output).any():
        print(f"NaN detected in {module.__class__.__name__}")

for module in model.modules():
    module.register_forward_hook(nan_hook)
```

### 12.3 Tensor Core Alignment

Tensor Core-friendly alignment is a useful optimization: dimensions that are multiples of 8 (BF16/FP16) or 16 (FP8/INT8) often map more efficiently onto Tensor Core kernels. This is a performance heuristic rather than a universal requirement — profile before reshaping a model around it.

```python
# Often slower: dimensions that don't align to Tensor Core tiles
model = nn.Linear(257, 513)

# Often faster: aligned dimensions
model = nn.Linear(256, 512)

# Commonly relevant for: batch size, sequence length, hidden dimensions,
# number of attention heads, vocabulary size
```
