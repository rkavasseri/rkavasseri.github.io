## Why this exists

GPU vendors now put most of their throughput into low-precision matrix units, while FP64 and FP32 fall behind. Kernels that cannot use matrix units lose ground with every hardware generation.

Radar workloads are complex-valued, phase-sensitive, and need wide dynamic range, which is exactly what AI-tuned libraries ignore. AMD in particular has no device-callable FFT that uses its matrix instructions, so radar pipelines make repeated round trips to memory.

## The direction

The target is **fused radar kernels on AMD**, measured against rocFFT, hipFFT, rocSOLVER and MAGMA. NVIDIA GPUs serve as correctness checks. The build order:

1. Fused range compression (built).
2. Fused RDA azimuth path.
3. Fused covariance and leading eigenvector for InSAR phase linking (first version built).
4. Back-projection.

## What has been learned so far

Standalone batched FFTs turned out to be memory-bound, so matrix cores only pay off inside fused or compute-bound kernels. The speed criterion now applies to fused use.

Split-precision arithmetic has a cost: three BF16 terms carry about 16 bits, so FP32 equivalence on BF16-only hardware needs a six- or nine-way split.
